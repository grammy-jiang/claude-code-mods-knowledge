# Claude Code 2.1.304: actual failed-reload recovery and candidate gates

**Date:** 2026-10-22, Australia/Sydney. **Issue:** [#110](https://github.com/grammy-jiang/claude-code-mods-knowledge/issues/110).
**Verdict:** PARTIAL QA acceptance; no 2.1.304 Claim promotion or Stable release.

## Executive finding

On one isolated Raspberry Pi 5 (Linux ARM64), an authenticated Claude Code
**2.1.304** native process demonstrated the complete lifecycle of an installed
local-scope Plugin:

| One continuous CLI session | Actual harmless QA prompt result |
| --- | --- |
| Working Plugin v0.0.1 | Hook refused before model inference: **0 turns** |
| Intentionally invalid Plugin v0.0.2 updated via official CLI and reloaded | Old Hook was unloaded; identical harmless prompt reached model: **1 turn** |
| Repaired Plugin v0.0.3 updated via official CLI and reloaded | New Hook registered; same prompt refused again: **0 turns** |

The two reload commands completed with **0 model turns** each. Reload summary
messages alone did not prove the safety Hook state; original native debug and
result events established the difference.

The same running host produced model-turn counts **[0, 0, 1, 0, 0]**. The
first-party SHA-pinned native 2.1.304 executable had SHA256
c487117526509ab6d2ee6013e14f181faf68d6d6afe6bb0d4b2b4a9feca5ecb3.
The harmless guard source returned to identical bytes at the end; no external
shell, file or managed-permission actions were available to the model.

**This proves restoration is possible after valid reload in the tested host.**
It does not eliminate the intervening fail-open window, establish equivalent
TUI behavior, or establish a safe production rollout procedure.

## Deterministic preflight must inspect the exact Plugin, not the marketplace

Native **claude plugin validate --strict** rejected the invalid v0.0.2
candidate (exit code 1) and accepted valid v0.0.3 (exit code 0). The official
Plugin update command itself returned success for both versions because
the fault-injection test deliberately bypassed the preflight.

The official [Plugin commands reference](https://code.claude.com/docs/en/plugins/cli-reference)
specifies that checking a Marketplace manifest does not inspect the actual
Hook/Skill files of the Plugins it references. Validation must target the
exact versioned Plugin package.

The new QA-only **scripts/guard_cli304_native_plugin.py** has two stages:

1. **preflight:** requires reviewed source-tree SHA256, Plugin identity and
   version, an official SHA-pinned 2.1.304 executable, no symlinks or special
   files, and a clean native strict validation on frozen copied bytes.
   It rejects known unguarded Hook warning output, even if the CLI exits zero.
   It does not perform installation and explicitly marks the active session
   as not yet verified.
2. **postflight-qa:** requires the installed bytes to match the reviewed
   preflight receipt and inspects genuine private native JSONL/debug records
   from a single continuous process. It verifies initial guard refusal,
   failed reload/lost guard, recovered Hook registration, and final refusal
   before model inference. This is evidence for one controlled QA session
   only, not a production-wide authorization to continue protected work.

The source checksum is intentionally distinguished from installation cache
metadata. The prior v0.0.2 cache acquired an **.orphaned_at** marker after
being superseded by v0.0.3. This volatile file is NOT part of the original
release package. We pin the clean v0.0.2 candidate separately, inspect the
obsolete cache's precise source files plus known metadata, and reject
candidate packages containing .orphaned_at. Silent omission of arbitrary
unknown files is not permitted.

The reviewed benign good and deliberately malformed negative packages are
under **evals/fixtures/cli304-recovery-20261022**. The negative fixture
must not be deployed.

## Independent real-host evidence

The independent **scripts/audit_cli304_update_recovery_evidence.py** replays
the original private host wire/debug events, frozen candidate checksums,
native strict validation and postflight QA gate. It generated the immutable
public report:
[2026-10-22-cli304-failed-reload-recovery-evidence.json](2026-10-22-cli304-failed-reload-recovery-evidence.json).

Original model text, session IDs, terminal traces, receipts, good and bad
candidate bytes, and official native executable are stored in a restricted
private evidence directory on the Raspberry Pi, NOT in Git. Replaying from
that persisted evidence copy generated byte-identical sanitized JSON.

The public CI test verifies source and audit fingerprints, exact candidate
trees and the continued HOLD decision. It does not pretend to run paid
inference. SHA256 and private traces support reproducibility but do not
provide a cryptographically signed host attestation.

## Interactive TUI reload is not yet proven

An additional TUI test established that the QA Mod was loaded and the original
guard fired. But after a blocked prompt, the composer retained input and the
attempted reload commands were not reliably submitted independently. No
valid TUI parser-failure/recovery transition was captured. Those runs are
**excluded**, not passed, and cannot substitute for this missing evidence.

## Unresolved production requirements

This QA checker cannot protect all independently running sessions. A
production update controller would need to install exactly the validated
bytes, quiesce protected actions during transition, verify every relevant
active Hook in every affected session or restart that session, and refuse
dependent actions while verification fails. **Such a production controller
is not implemented here.** Do not present the QA preflight/postflight as a
universal fail-closed fix.

Follow-up: complete a reliable TUI reload comparison, positive human approval
and managed permission precedence, commands/tools retention separate from
Hooks, additional installed scopes, and independent Claim review. All new
CLI304 Claims and Stable release remain HOLD. Agent Communication is a
separate excluded project.
